<objective>
Replace the plaintext "Not found" 404 that currently greets humans at
https://api.lqwdclaw.bot/ with a branded, refined-editorial marketing page
explaining what LQWDClaw-NodeOps is and the three ways agents can start.
Machine paths (/v1/*) are untouched; only the root path gets HTML.
</objective>

<design_direction>
Refined editorial, per frontend-design skill guidance — commit to one bold
aesthetic, avoid generic AI defaults.

- Palette: cream #F5F1E8 background, LQWD navy #1A3C79 dominant, near-black
  body ink, muted gold #B8935A accent on links/labels only
- Typography: Instrument Serif (variable) headings, Instrument Sans body,
  JetBrains Mono code — explicitly NOT Inter / Roboto / Arial
- Layout: magazine-style — hero headline, three-column path grid, dark code
  snippet, next-steps row, footer
- Motion: staggered fade-up on load, underline-thickness grow on hover,
  `prefers-reduced-motion` respected
- Detail: SVG noise filter overlay for paper-grain feel, hairline rules in
  semi-transparent navy
- No JavaScript, no analytics beacons, no external dependencies beyond
  Google Fonts via CDN
</design_direction>

<action>
The Caddyfile already has a `handle /` block (added in this phase) that
serves `/etc/caddy/landing/landing.html` via file_server. Confirm the
block placement — it MUST be before the catch-all `handle {}` so Caddy's
path-length-longest-match picks `/` exact for the root and falls through
to the catch-all for everything else.

Verify the ordering visually:
```bash
grep -nE 'handle (/v1|/admin|/|/\{|\{)' scripts/Caddyfile
```

Expected order top-to-bottom:
1. `/v1/l402/*`
2. `/v1/internal/*`
3. `/v1/mcp*`
4. `/v1/discovery`
5. `/v1/health`
6. `/admin/*`
7. `/` (new)
8. catch-all `{}`

Caddy matches most-specific path first regardless of file order, but we
keep the file visually ordered for human reviewers.
</action>

<acceptance_criteria>
- `grep -c 'handle /' scripts/Caddyfile` returns >= 7 (all the handle blocks)
- `grep -A1 'handle /$' scripts/Caddyfile | grep -q 'root \* /etc/caddy/landing'` exits 0
- `grep -q 'file_server' scripts/Caddyfile` exits 0

<title>VM deploy — install landing file + reload Caddy</title>

<read_first>

- scripts/landing.html

<action>
**On the VM (ubuntu@71.19.249.198):**

```bash
cd /opt/lqwdclawnode && git pull

sudo mkdir -p /etc/caddy/landing
sudo install -m 644 -o root -g caddy \
    /opt/lqwdclawnode/scripts/landing.html \
    /etc/caddy/landing/landing.html

    /opt/lqwdclawnode/scripts/Caddyfile \

sudo systemctl reload caddy
sudo journalctl -u caddy -n 15 --no-pager
```

Expected: `Valid configuration`, reload succeeds, no new errors in
journal. The two `X-Forwarded-Proto` warnings from prior phases will
still appear — they're cosmetic and unrelated to this change.

```bash
curl -sk -o /dev/null -w "HTTP %{http_code} bytes=%{size_download}\n" \
    https://127.0.0.1/ \
    --resolve api.lqwdclaw.bot:443:127.0.0.1 -H "Host: api.lqwdclaw.bot"

curl -sk https://127.0.0.1/ \
    --resolve api.lqwdclaw.bot:443:127.0.0.1 -H "Host: api.lqwdclaw.bot" \
```

Expected: HTTP 200 with a multi-KB response body containing the
`<!doctype html>` prefix and the LQWDClaw headline text.
