# Phase 16.1: Gateway Safety Hardening - Context

**Gathered:** 2026-04-15
**Status:** Ready for planning
**Source:** Code review report + manual code validation

<domain>
## Phase Boundary

Fix three confirmed safety issues in the lnd-gateway discovered during code review. All fixes are in the Go gateway binary (`lnd-gateway/`). No frontend, no new features — pure correctness fixes to existing write operation handlers.

</domain>

<decisions>
## Implementation Decisions

### Fix 1: Budget Leakage on Unconfirmed Operations (Critical)
- `audit/logger.go:DailySpend()` counts ALL records with `response_code < 400`, including `202 Accepted` entries from confirmation-gated operations
- `write.go` logs `202 Accepted` audit entries with `AmountSats` immediately when creating confirmations for OpenChannel, CloseChannel, SendOnChain
- `confirm/manager.go:Reject()` deletes from memory without reversing the audit entry
- Result: unconfirmed/rejected/expired operations permanently burn daily budget
- **Fix approach:** Add `AND response_code != 202` to the `DailySpend()` SQL query. This excludes pending confirmations from budget calculations. When a confirmation is actually executed (confirmed), the execution handler logs a new audit entry with `200 OK` which WILL be counted. This is the minimal, correct fix.
- Affected files: `internal/audit/logger.go` (DailySpend query), `internal/audit/logger_test.go` (test for exclusion)

### Fix 2: SendPayment Bypasses Confirmation Flow (High)
- `write.go:SendPayment()` calls `d.LND.SendPayment()` directly after budget check
- All other destructive write ops (OpenChannel, CloseChannel, SendOnChain) use `d.Confirm.Create()` and return `202 Accepted` with `confirmation_required: true`
- SendPayment is inconsistent — executes immediately with no admin confirmation gate
- **Fix approach:** Refactor SendPayment to match OpenChannel pattern: create confirmation via `d.Confirm.Create()`, return `202 Accepted`, log audit with 202. Actual execution happens when admin confirms via `/v1/confirm/{id}`.
- Affected files: `internal/handlers/write.go` (SendPayment handler), `internal/handlers/write_test.go` (if exists)

### Fix 3: CloseChannel gRPC Stream Blocks Indefinitely (Medium)
- `lnd/grpc.go:CloseChannel()` at line 359 calls `stream.Recv()` with no timeout
- If LND hangs or is heavily loaded, the HTTP goroutine blocks forever
- **Fix approach:** Wrap the context with `context.WithTimeout(ctx, 60*time.Second)` before the `stream.Recv()` call. 60s matches the OpenChannel timeout pattern already established.
- Affected files: `internal/lnd/grpc.go` (CloseChannel method)

### Claude's Discretion
- Test coverage for all three fixes
- Whether to add similar timeouts to other gRPC streaming calls (SendPayment already has TimeoutSeconds)

</decisions>

<specifics>
## Specific Ideas

- The DailySpend fix is a one-line SQL change but needs a test proving 202 entries are excluded
- SendPayment refactor should preserve the existing idempotency and budget check logic, only changing the execution path to use confirmation
- CloseChannel timeout should use `context.WithTimeout` not `time.After` to properly cancel the gRPC stream

</specifics>

<deferred>
## Deferred Ideas

- Global mutex elimination in budget enforcer (performance, not correctness)
- SQLite BUSY retry logic (edge case, not blocking)
- HTTP server ReadTimeout/WriteTimeout (defense-in-depth, separate concern)
- Refactoring write handlers to use a NodeService interface (maintainability, not safety)

</deferred>
