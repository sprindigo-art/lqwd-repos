<objective>
Fix two independent safety issues: (1) DailySpend() incorrectly counts 202 Accepted audit entries from unconfirmed operations, allowing budget exhaustion via spam, and (2) CloseChannel gRPC stream blocks indefinitely on Recv() with no timeout.
</objective>

<tasks>

<task id="1" type="execute">
<title>Exclude 202 Accepted from DailySpend budget calculation</title>

<read_first>
- lnd-gateway/internal/audit/logger.go
- lnd-gateway/internal/audit/logger_test.go
- lnd-gateway/internal/handlers/write.go (reference: how 202 entries are created)
</read_first>

<action>
In `lnd-gateway/internal/audit/logger.go`, modify the `DailySpend()` method's SQL query.

Current query (around line 156):
```sql
SELECT COALESCE(SUM(amount_sats), 0) FROM audit_log
WHERE op_type IN ('payment', 'channel_open', 'onchain_send', 'rebalance')
AND response_code < 400
AND timestamp > datetime('now', '-24 hours')
```

Change `AND response_code < 400` to `AND response_code < 400 AND response_code != 202`:
```sql
SELECT COALESCE(SUM(amount_sats), 0) FROM audit_log
WHERE op_type IN ('payment', 'channel_open', 'onchain_send', 'rebalance')
AND response_code < 400
AND response_code != 202
AND timestamp > datetime('now', '-24 hours')
```

This excludes pending confirmation entries (202 Accepted) from budget calculations. When an operation is actually confirmed and executed, the execution path logs a new entry with 200 OK which WILL be counted.

In `lnd-gateway/internal/audit/logger_test.go`, add a test function `TestDailySpend_Excludes202`:
1. Create a test audit logger with a temp SQLite DB
2. Insert an audit entry with response_code=202, op_type="channel_open", amount_sats=500000
3. Insert an audit entry with response_code=200, op_type="payment", amount_sats=100000
4. Call DailySpend() and assert the result equals 100000 (not 600000)
5. This proves 202 entries are excluded from budget calculations
</action>

<acceptance_criteria>
- `logger.go` contains `AND response_code != 202` in the DailySpend query
- `logger_test.go` contains `func TestDailySpend_Excludes202`
- `cd lnd-gateway && go test ./internal/audit/ -run TestDailySpend_Excludes202 -v` exits 0
- `cd lnd-gateway && go test ./internal/audit/ -v` exits 0 (all existing tests still pass)
</acceptance_criteria>
</task>

<task id="2" type="execute">
<title>Add 60-second timeout to CloseChannel gRPC stream</title>

<read_first>
- lnd-gateway/internal/lnd/grpc.go
- lnd-gateway/internal/handlers/write.go (reference: how CloseChannel is called)
</read_first>

<action>
In `lnd-gateway/internal/lnd/grpc.go`, modify the `CloseChannel` method (around line 331).

Add a `context.WithTimeout` wrapping before the gRPC call. Insert BEFORE the `c.lightning.CloseChannel(ctx, closeReq, ...)` call:

```go
// Add 60s hard deadline to prevent indefinite blocking on stream.Recv()
closeCtx, closeCancel := context.WithTimeout(ctx, 60*time.Second)
defer closeCancel()
```

Then change the two references from `ctx` to `closeCtx`:
1. `stream, err := c.lightning.CloseChannel(closeCtx, closeReq, c.macaroons.ChannelAdmin)` (was `ctx`)

The `stream.Recv()` call on the next line will automatically respect the `closeCtx` deadline since the stream was created with it.

Ensure `"context"` and `"time"` are in the import block (both should already be present).
</action>

<acceptance_criteria>
- `grpc.go` contains `context.WithTimeout(ctx, 60*time.Second)` in the CloseChannel method
- `grpc.go` contains `closeCtx, closeCancel := context.WithTimeout`
- `grpc.go` contains `defer closeCancel()`
- `grpc.go` contains `c.lightning.CloseChannel(closeCtx,`
- `cd lnd-gateway && go build ./...` exits 0
- `cd lnd-gateway && go test ./... 2>&1 | tail -5` shows no failures
</acceptance_criteria>
</task>
