## Why this phase exists

Phase 16.1 ("Gateway Safety Hardening") shipped with `7/7 UAT passed` recorded — but the UAT was run in `GATEWAY_MOCK=true`, where `ConfirmOperation` short-circuits at `handlers.go:165-181` before the executor runs. The real production path is structurally broken in three independent ways:

1. **Executor missing case for `/v1/payments/send`** (`internal/lnd/executor.go:23-47`)
2. **JSON tag mismatch handler ↔ executor** for OpenChannel, CloseChannel, SendOnChain — handler structs use `push_sats` / `chan_id` / `address` / `amount_sats`; executor unmarshals into `lnd.OpenChannelRequest` / `lnd.CloseChannelRequest` / `lnd.SendCoinsRequest` which use `push_sat` / `channel_point` / `addr` / `amount`
3. **DailySpend op_type filter mismatch** — confirmed ops log as `confirmed_/v1/payments/send`, but `audit.DailySpend` filters `op_type IN ('payment',…)`. Real outflows count as zero; the kill switch enforces nothing.

Plus three further safety holes:
4. **Rebalance bypasses confirmation entirely** (`analytics.go:108-200` — agent-callable, executes immediately up to `MaxRebalanceFeeSats`)
5. **`/v1/admin/restart-lnd` has no `RequireAdmin`** (`main.go:219` — comment even says "agent can call")
6. **L402 `/v1/l402/pay` never `Store`s its idempotency response** + has no refund path on LND failure (paid-but-unrecoverable state)

If 16.1's branch deploys today: every admin-confirmed payment returns 502, every confirmed CloseChannel fails at LND, confirmed OpenChannel silently sends `push_sats=0`, the daily kill switch enforces nothing, and any agent-token holder (or LLM prompt injection) can drain liquidity via Rebalance or restart LND at will.

## What this phase does

Fixes the six issues above + deletes 61 macOS Finder `* 2.*` duplicates that break local `go build`.

### Fix 1 — Delete macOS duplicates (trivial unblocker)
`lnd-gateway/` has 61 untracked `* 2.go` / `* 2.html` / `* 2.json` files from a Finder copy operation. They break local `go build`. Delete all of them. They're untracked, so this is a no-op for git history.

### Fix 2 — Executor: SendPayment case + JSON tag alignment
**Root cause:** Two independent bugs in the same flow.

- The `/v1/payments/send` case is missing from `executor.go`'s switch.
- The internal `lnd.OpenChannelRequest` / `lnd.CloseChannelRequest` / `lnd.SendCoinsRequest` / `lnd.SendPaymentRequest` types have JSON tags that don't match what the handlers serialize into the confirmation `RequestBody`.

**Fix approach:**
- Add the missing `/v1/payments/send` case calling `e.client.SendPayment`.
- **Align JSON tags by changing the LND request types** (not the handlers). The handler shape is the public API contract; the LND types are internal Go structs. `grpc.go` consumes them by Go field name (`req.PushSat`, `req.ChannelPoint`, `req.Addr`), not by JSON tag, so changing the JSON tags is safe.
- Mapping:
  - `OpenChannelRequest.PushSat`: `json:"push_sat"` → `json:"push_sats"`
  - `CloseChannelRequest.ChannelPoint`: `json:"channel_point"` → `json:"chan_id"`
  - `SendCoinsRequest.Addr`: `json:"addr"` → `json:"address"`
  - `SendCoinsRequest.Amount`: `json:"amount"` → `json:"amount_sats"`
  - `SendPaymentRequest.FeeLimitSat`: `json:"fee_limit_sat"` → `json:"fee_limit_sats"`
  - `SendPaymentRequest.TimeoutSeconds`: keep (matches handler)
- Update `CloseChannelRequest`'s gRPC translation in `grpc.go` to interpret `ChannelPoint` as either `txid:vout` (current) or as a CLN-style `chan_id` if the handler ever sends one. **Decision:** keep `txid:vout` semantics — the agent already passes `txid:vout` in the `chan_id` field. Just align the JSON tag.
- Add `executor_test.go` covering all 4 ops: assert that round-tripping handler-shape JSON through the executor reaches the LND client with non-zero, correct fields.

### Fix 3 — DailySpend op_type filter
**Root cause:** Confirmation handler writes audit rows with `OpType: "confirmed_" + op.Endpoint` (e.g. `confirmed_/v1/payments/send`). `DailySpend` filters `op_type IN ('payment', 'channel_open', 'onchain_send', 'rebalance')` — never matches.

**Fix approach:** Map `op.Endpoint` to its canonical `op_type` (`/v1/payments/send` → `payment`, `/v1/channels/open` → `channel_open`, etc.) at the audit-write site in `ConfirmOperation` (`handlers.go:171-211`). Keep the `confirmed_` prefix off the daily-spend column entirely; record the "this came from a confirmation" fact in the `Endpoint` field or a new column if needed (keep it in `Endpoint` for now).
- Add a `endpointToOpType` helper.
- Update `DailySpend` test to verify: audit a confirmed payment → `DailySpend` returns the amount.

### Fix 4 — Gate Rebalance and RestartLND
- **RestartLND**: wrap with `middleware.RequireAdmin` in `main.go:219`. Remove the `// agent can call` comment.
- **Rebalance**: route through `Confirm.Create` (mirror SendPayment pattern). Add an executor case `/v1/analytics/rebalance` calling `e.client.Rebalance`.

### Fix 5 — L402 idempotency Store + refund path
- After a successful `/v1/l402/pay`, call `Idempotency.Store(req.IdempotencyKey, "/v1/l402/pay", 200, body)` so retries replay correctly.
- On any error after `CheckAndReserve` succeeded, release the reservation (or store the failure response with a non-200 status, depending on the idempotency package's API). The current behavior — silent 24h lock on a failed payment — is unacceptable.
- For the L402 server side (`internal/handlers/l402.go`), audit whether token consumption happens before or after a successful LND fetch; defer that hardening to a follow-up if the consume-then-fail window is small.
