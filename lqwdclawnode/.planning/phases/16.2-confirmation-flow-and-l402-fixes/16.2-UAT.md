# Phase 16.2 UAT

**Goal:** prove the five code fixes behave correctly against a real LND. Phase 16.1's UAT was recorded as 7/7 passing but ran in mock mode, where `ConfirmOperation` returns 200 before ever touching the executor. This UAT **must** run with `GATEWAY_MOCK=false` — first against signet (UAT-01 through UAT-09), then against mainnet (UAT-10 and UAT-11) after the deploy prereq is done.

## Prerequisites (signet — UAT-01..09)

- signet `lnd` running and unlocked (see `scripts/SIGNET-SETUP.md`)
- `ADMIN_TOKEN` and `AGENT_TOKEN` exported
- Gateway compiled from branch `fix/phase-16.2-confirmation-flow` and running with `GATEWAY_MOCK=false`
- Peer node available for OpenChannel test (≥ 150k sats available on-chain)

## Prerequisites (mainnet deploy — UAT-10..11)

Phase 16.2 dropped `FAUCET_CHANNEL_SIZE_SATS` from 100_000 to 20_000. The production VM's `/lnd/lnd.conf` currently has `minchansize=2000000` (2M sats, from the pre-16.2 setup) which will reject every faucet open as below its own minimum. **Must be updated before deploying the 16.2 gateway build:**

```bash
ssh ubuntu@71.19.249.198
sudo cp /lnd/lnd.conf /lnd/lnd.conf.pre-16.2.bak                 # rollback point
sudo sed -i 's/^minchansize=.*/minchansize=20000/' /lnd/lnd.conf
grep ^minchansize /lnd/lnd.conf                                  # verify: minchansize=20000
sudo systemctl restart lnd
# Wait 10–20s for LND to come up, then unlock the wallet:
lncli unlock
# Sanity check:
lncli getinfo | grep -E '"synced_to_chain"|"block_height"'
```

Notes:
- Setting `minchansize=20000` affects BOTH outgoing opens (what the gateway can open) AND incoming channel requests (what peers can open toward our node). Both directions are desired for the faucet model.
- `maxchansize=500000000` stays unchanged.
- If the restart fails or `lncli unlock` hangs, revert with `sudo cp /lnd/lnd.conf.pre-16.2.bak /lnd/lnd.conf && sudo systemctl restart lnd`.

## Tests

### UAT-01 — Confirmed SendPayment reaches LND

**Why:** CR-02 (missing executor case) and CR-01 (JSON tag mismatch for `fee_limit_sats`) both in the payment flow.

1. Create an invoice on peer: `lightning-cli --network=signet invoice msatoshi=1000000 label=uat-16.2-01 description=uat`
2. Agent: `POST /v1/payments/send` with `payment_request=<invoice>`, `amount_sats=1000`, `fee_limit_sats=50`, `idempotency_key=uat-01`
3. Expect: 202 Accepted, `confirmation_required=true`, `operation_id` present
4. Admin: `POST /v1/confirm` with that `operation_id`
5. **Expect: 200 OK with `data.payment_preimage` populated** — NOT 502 "unknown endpoint for execution"
6. Check `lnd` logs: payment settled, preimage matches
7. `POST /v1/audit/recent` — expect a `200 OK` row with `op_type="payment"` and `amount_sats=1000`

### UAT-02 — Confirmed CloseChannel reaches LND

**Why:** CR-01 — `chan_id` tag mismatch caused "invalid channel_point format" at LND.

1. Pick an existing channel: `POST /v1/channels/list` → pick `channel_point`
2. Agent: `POST /v1/channels/close` with `chan_id=<channel_point>`, `force=false`, `idempotency_key=uat-02`
3. Expect 202 + operation_id
4. Admin: `POST /v1/confirm` with operation_id
5. **Expect: 200 OK with `data.closing_txid`** — NOT 502 "invalid channel_point format"
6. `bitcoin-cli` confirm the closing tx broadcast

### UAT-03 — Confirmed OpenChannel preserves push_sats

**Why:** CR-01 — `push_sats` tag mismatch silently dropped the push amount (agent asked for 25k, peer received 0).

1. Pick peer pubkey
2. Agent: `POST /v1/channels/open` with `node_pubkey=<peer>`, `local_funding_amount=100000`, `push_sats=25000`, `idempotency_key=uat-03`
3. Expect 202 + operation_id
4. Admin: `POST /v1/confirm` with operation_id
5. After confirmation, `POST /v1/channels/pending` on the peer node
6. **Expect: remote balance on the pending channel == 25000 sats** — NOT 0

### UAT-04 — Confirmed SendOnChain preserves address + amount

**Why:** CR-01 — `address`/`amount_sats` tag mismatch.

1. Get a peer on-chain address
2. Agent: `POST /v1/onchain/send` with `address=<peer_addr>`, `amount_sats=20000`, `sat_per_vbyte=2`, `idempotency_key=uat-04`
3. Expect 202 + operation_id
4. Admin: `POST /v1/confirm`
5. **Expect: 200 OK with a txid**
6. `bitcoin-cli -signet gettransaction <txid>` — verify output of 20000 sats to the peer address

### UAT-05 — Rebalance requires confirmation

**Why:** P-3 — Rebalance bypassed confirmation entirely.

1. Agent: `POST /v1/rebalance` with realistic outgoing/incoming chan IDs
2. **Expect: 202 Accepted, `confirmation_required=true`, `operation_id` present** — NOT 200 OK
3. Admin: `POST /v1/confirm` with operation_id → expect 200 OK with rebalance result

### UAT-06 — RestartLND requires admin token

**Why:** P-4 — endpoint was bypassing RequireAdmin.

1. Agent token: `POST /v1/admin/restart-lnd` → **expect 403 Forbidden**
2. Admin token: `POST /v1/admin/restart-lnd` → expect 200 OK, systemd restart trigger file written

### UAT-07 — DailySpend reflects confirmed payments

**Why:** CR-03 — `op_type="confirmed_*"` never matched the DailySpend filter.

1. Before: `POST /v1/audit/summary` → note `daily_spend_sats`
2. Execute UAT-01 (confirmed SendPayment of 1000 sats)
3. After: `POST /v1/audit/summary` → **expect `daily_spend_sats` to have increased by 1000** — NOT unchanged

### UAT-08 — L402Pay idempotent replay

**Why:** CR-04 — `/v1/l402/pay` never Stored its success response; retries locked for 24h.

1. Set up an external L402 endpoint (or use `l402_payment_test.sh` if present)
2. Agent: `POST /v1/l402/pay` with `url=<endpoint>`, `max_sats=100`, `idempotency_key=uat-08`
3. Expect 200 OK with receipt
4. Immediately repeat the same request (same idempotency_key)
5. **Expect: identical 200 OK** with `X-Idempotent-Replay: true` header — NOT 409 "duplicate request in progress"

### UAT-09 — L402Pay releases reservation on pre-payment failure

**Why:** CR-05 — no refund path; pre-payment failures left the reservation stuck.

1. Agent: `POST /v1/l402/pay` with `url=https://nonexistent.invalid`, `max_sats=100`, `idempotency_key=uat-09`
2. Expect 502 (DNS failure before any LND call)
3. Retry the same request (same idempotency_key) after fixing the URL
4. **Expect: 200 OK on retry** — NOT 409 "duplicate request in progress"

## Mainnet tests (run AFTER signet UAT-01..09 pass AND the mainnet prereq above is done)

### UAT-10 — LND mainnet accepts 20k minchansize

**Why:** Guards against the deploy prereq being skipped. A 16.2 gateway deployed against an LND still configured with `minchansize=2000000` would silently reject every faucet open with a generic gRPC error; this test catches that before real users hit it.

1. SSH into the mainnet VM: `ssh ubuntu@71.19.249.198`
2. Confirm the live lnd.conf:
   ```bash
   grep ^minchansize /lnd/lnd.conf
   ```
   **Expect:** `minchansize=20000`
3. Confirm LND is running with that setting (the config is read at start, so prereq restart must have happened):
   ```bash
   sudo systemctl status lnd | grep -E "Active|Main PID"
   # Last restart timestamp should be AFTER the sed command in the prereq
   ```
4. Ask LND to dry-run a 20k channel-open policy check with `--connect` to a peer you control (does NOT broadcast — fails on peer unreachable, but passes policy first):
   ```bash
   lncli connect <test-peer-pubkey>@<test-peer-host>:9735 2>/dev/null
   lncli openchannel --node_key=<test-peer-pubkey> --local_amt=20000 --push_amt=1354 --sat_per_vbyte=2 --connect=<test-peer-host>:9735 --dry-run 2>&1 | head -5 || true
   ```
   **Expect:** no `chan size of X sats is below minimum of Y sats` error. Any other error (peer unreachable, insufficient on-chain funds) is acceptable — we only care that policy validation passes.

### UAT-11 — Mainnet faucet open end-to-end

**Why:** The only real proof that the full Phase 16.2 chain — registration → slot reservation → `OpenChannel` with 20k size + 1,354 push → confirm flow → LND accepts → channel broadcasts — works on mainnet. Everything prior to this UAT was mock, signet, or static analysis.

**Cost:** ~20_000 sats locked in channel + on-chain open fee (~500 sats at low priority). Funds return on channel close.

**Setup:** you (the operator) need a throwaway wallet with a reachable pubkey — phoenix/zeus mobile wallet, or a second LND instance. Record its `pubkey@host:port`.

1. Register a fresh agent via the CF-Access-protected registration endpoint with the throwaway pubkey as the faucet channel target:
   ```bash
   curl -sS -X POST https://gateway.lqwdclaw.bot/v1/internal/accounts/register \
     -H "CF-Access-..." \
     -H "Content-Type: application/json" \
     -d '{"email":"uat-11@lqwd.test","pubkey":"<throwaway-pubkey>","node_uri":"<throwaway-pubkey>@<host>:9735"}'
   ```
   **Expect:** 200 OK with an `api_key` and a `grant_id`.
2. Poll the channel-grant status:
   ```bash
   curl -sS -H "Authorization: Bearer <api_key>" \
     https://gateway.lqwdclaw.bot/v1/internal/accounts/me | jq '.channel_grant'
   ```
   **Expect (within ~30s):** `status: "pending_open"` → `status: "open"` with a `funding_txid`.
3. On the throwaway wallet, verify the incoming channel:
   - **Expect:** channel of capacity 20,000 sats, your-side (inbound) balance = 1,000 sats (the 1,354 push minus the 354-sat channel reserve).
   - 1,000 sats is the spendable amount. Reserve (354) is locked.
4. Verify audit trail from the gateway:
   ```bash
   curl -sS -X POST https://gateway.lqwdclaw.bot/v1/audit/recent -H "Authorization: Bearer $ADMIN_TOKEN" | jq '.entries[] | select(.endpoint=="channels_open" or .op_type=="channel_open")'
   ```
   **Expect:** one `channel_open` entry with `amount_sats=20000`.
5. Cleanup: from the throwaway wallet, initiate a cooperative close to return the 19,000 sats on-chain. Confirm the close tx propagates.

**Fail conditions:**
- Registration returns 200 but grant status stays `pending_open` > 60s: check `systemctl status lnd-gateway` logs for `channel size of X is below minimum`. If that appears, prereq was skipped — revisit.
- Peer-side balance shows 1,354 (not 1,000): reserve math is wrong. Check LND dust limit on that commitment output; may need to tune `FAUCET_PUSH_SATS` for this node's actual dust setting.
- Grant jumps straight to `failed`: read `channel_grants.error_message` — common causes are peer unreachable, insufficient on-chain, or LND still reporting old minchansize (confirms prereq wasn't applied live).

### Unexpected issues discovered and fixed during UAT (NOT 16.2 regressions — pre-existing prod bugs)

Both discovered as signet UAT failures; confirmed present on mainnet before proceeding; both fixed before deploy.

1. **`pay.macaroon` lacked `onchain:write`** (pre-existing since v1 setup). `internal/lnd/grpc.go:506` shows `SendCoins` uses `c.macaroons.Pay`. Per `SIGNET-SETUP.md` / `SETUP-GUIDE.md` Step 8, the pay macaroon was baked with `offchain:read offchain:write` only — no on-chain perms. Result: every on-chain send in production would have returned `permission denied`. Rebaked with `offchain:read offchain:write onchain:read onchain:write` on both signet and mainnet.

2. **Mainnet `minchansize=2000000`** (stale `SETUP-GUIDE.md` template value; 20x too high for 16.2's 20k faucet default). Changed to `minchansize=20000`. Required brief mainnet LND restart. (The gateway is still auto-unlocked post-restart on this VM — no manual unlock was needed.)
