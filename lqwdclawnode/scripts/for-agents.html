Overview

Onboard to Lightning.

The product LQWD offers today is a free mainnet Lightning channel for AI agents running their own node. MCP is the management surface for registering and checking channel status. There is no paid service at this time — adding paid liquidity for use is a later version.

The product

A free mainnet channel, on registration

Agents running a Bitcoin mainnet Lightning node (LND or LDK) register with their pubkey + node_uri and receive a one-time channel from LQWD. 20,000 sat capacity, 1,354 sats pushed to your side. Operator-funded, zero cost to the agent. This is the only product in v1.

No node yet? SaturnZap — an OSS CLI + MCP Lightning wallet from LQWD — stands one up on mainnet in minutes.

→ Channel faucet
Management surface

Same product, over MCP

Claude Desktop, Cursor, Cline, or any MCP client can call the same registration + status tools over the Model Context Protocol instead of curl. Bearer-authed with the api_key you get on registration. Not an alternate onboarding path — just a different transport for the one product.

→ MCP setup

The call

Registration is one POST with your pubkey and node_uri. LQWD opens the channel to you asynchronously and returns an api_key (prefix lqwd_) plus a channel_status_url for polling the open. The api_key exists so you can check channel status, retry a failed open, and use the MCP management surface — it is not a standalone product.

curl — channel faucet registration
# One call, one free mainnet channel
curl -X POST https://api.lqwdclaw.bot/v1/internal/accounts/register \
  -H "Content-Type: application/json" \
  -d '{
    "name": "<pick-unique-node-name>",
    "pubkey": "<66-char-hex-pubkey>",
    "node_uri": "<pubkey>@<host>:9735"
  }'

Save the api_key — you can rotate it, but not retrieve it. Rate limited to 3 registrations per IP per hour. A pubkey and node_uri are required — there is no account-only path in v1.

The channel faucet

Run your own node? Request inbound liquidity.

If you operate (or plan to operate) a Bitcoin mainnet Lightning node, LQWD will open a channel to you as part of tier-1 registration. One-time grant, operator-funded, ~20,000 sat capacity with a small push to give you some immediate outbound.

Channel specifics

FieldValue
Capacity20,000 sats
Push to your side1,354 sats (1,000 spendable + 354 sat p2wsh reserve)
LQWD side~18,646 sats outbound (your inbound liquidity)
Fee rateOperator-chosen based on mempool
Grants per agentOne (tier-1)

Requirements

  • A mainnet Lightning node — Bitcoin mainnet, not signet or regtest. LND, LDK (via SaturnZap), or any BOLT-compatible implementation.
  • Publicly reachable at the host:port in your node_uri — any port you advertise in the URI must accept inbound TCP from the public internet. 9735 is the Lightning default; SaturnZap v1.1.0+ uses 9735 on mainnet (pre-1.1.0 used 9737). Confirm with sz connect-info before opening firewall rules.
  • Your node_uri — pubkey@host:port format
  • Peer-connect to LQWD BEFORE registering — see the next section. Skipping this step risks counting toward the 3-failure ban if LQWD's ConnectPeer attempt fails for any reason.
  • Run a reachability pre-flight (below) — confirm LQWD can dial you before you consume a registration slot. Your IP has a limit of 3 registrations per hour.
Ban policy. Channel-open failures count toward a rolling 3-failure threshold per pubkey. A single transient glitch will NOT ban you — but three consecutive failures will. If you hit that wall, fix your reachability, then use POST /v1/internal/channel/retry with your api_key to retry without re-registering (preserves your api_key, doesn't consume the /register rate limit). If your pubkey does get banned, operators can clear it manually on request.

Pre-flight: two things to get right before you register

1. Configure a node alias. LQWD opens announced (public) channels into your node. Nodes without a configured alias reject announced channels outright — your registration will fail with Channel request rejected / "Node alias is not configured" in your node's log, and your pubkey will be auto-banned. Set one before bringing the node up:

bash — set node alias
# LND: edit ~/.lnd/lnd.conf and set
#   alias=<pick-unique-node-name>
# then restart lnd.

# SaturnZap: the LDK config lives at
#   ~/.local/share/saturnzap/bitcoin/ldk/config.toml
# Add a line: node_alias = "<pick-unique-node-name>" and restart the daemon.

2. Peer-connect to LQWD before registering. The faucet calls ConnectPeer on your node when it opens the inbound channel. If that call fails — transient network glitch, wrong port advertised, firewall race — your pubkey is auto-banned and you have to ask an operator to unban. Avoid the trap by establishing the peer connection before registering. Once the peer exists on your side, LQWD's ConnectPeer is a no-op.

Fetch LQWD's own node URI from discovery:

curl — get LQWD's node URI
curl -s https://api.lqwdclaw.bot/v1/discovery \
  | jq -r .data.lqwd_node.uri

Then connect from your node:

bash — peer-connect (LND)
# LND
lncli connect "<lqwd-uri>"

# SaturnZap
sz peers add "<lqwd-uri>"

# Verify — match on the 66-char hex pubkey from <lqwd-uri>,
# NOT a friendly name. LQWD's node advertises the alias
# "LQWD-AI-Launchpad" on the network — that's a display label,
# not an identifier to match on.
lncli listpeers   # or: sz peers list

Confirm the peer with the pubkey portion of <lqwd-uri> shows as connected. The node's alias will display as LQWD-AI-Launchpad on the network — that's a human-readable display label, not the identifier you should match on. Always match on the 66-char hex pubkey. If the peer-connect itself fails, your reachability or node URI is wrong — fix that before registering, not after.

Pre-flight: reachability check (no rate-limit cost)

Once your node is up and peered, ask LQWD to dial you back from the gateway side. This is a free, no-account, no-rate-limit probe — if it reports reachable: true, your subsequent /register will almost certainly succeed.

curl — pre-flight reachability check
curl -X POST https://api.lqwdclaw.bot/v1/internal/accounts/reachability-check \
  -H "Content-Type: application/json" \
  -d '{
    "pubkey": "<66-char-hex>",
    "node_uri": "<pubkey>@<host>:<port>"
  }'

Response shape: { ok: true, data: { reachable: true } } on success, or { reachable: false, error: "<lnd-error-text>" } with a diagnostic string. If the check fails, fix the underlying issue (firewall not attached, wrong port advertised, node not listening, etc.) and re-run — this endpoint is free to call.

If something goes wrong: retry without re-registering

If a registration ends up in status: failed (for example your firewall wasn't actually attached at registration time), use the retry endpoint to kick off a fresh channel-open attempt without creating a new account. Your api_key carries over, the /register rate limit is not consumed, and your failure history is preserved (each retry still counts toward the 3-failure ban threshold).

curl — retry a failed channel open
curl -X POST https://api.lqwdclaw.bot/v1/internal/channel/retry \
  -H "Authorization: Bearer lqwd_YOUR_KEY"

Returns 202 with a new channel_id on success, 409 if your latest grant isn't in failed state (nothing to retry), 404 if you never registered a node_uri, or 403 if you've already hit the 3-failure ban.

Don't have a node yet? SaturnZap is LQWD's open-source CLI + MCP Lightning wallet (Python + LDK). It stands up a mainnet Lightning node on a fresh host in minutes with no bitcoind sync. An MCP-capable agent with both SaturnZap and LQWD configured can boot the node, capture pubkey@host:port, and register for the channel in a single prompt.

SaturnZap install reference

The install shape below is declarative — it describes the commands an operator runs on their own host. LQWD does not host a shell wrapper; there is no | sh pattern on this domain.

Prerequisite: uv (Astral's Python tool manager). Install from the packaging source of your choice — Homebrew, apt, dnf, or the official installer at docs.astral.sh/uv/. Do not pipe remote scripts straight into a shell.

With uv present, install SaturnZap from the GitHub release page using the explicit --find-links form. This is also the canonical install command published in /v1/discovery and /.well-known/ai-agent-trust.json.

bash — SaturnZap install reference (v1.3.1)
# Pinned release, explicit index, no curl-to-shell.
uv tool install saturnzap --find-links https://github.com/lqwdtech/SaturnZap/releases/expanded_assets/v1.3.1
sz --version

# Initialize the wallet. v1.3.0 safety flags:
#   --backup-to writes the encrypted mnemonic to a file of your choosing
#   --no-mnemonic-stdout keeps the recovery phrase out of shell history
export SZ_PASSPHRASE="..."
sz init --backup-to ~/.saturnzap-mnemonic --no-mnemonic-stdout

# Persist as a systemd service.
sz service install
systemctl start saturnzap

# Print your node identifier for the /register payload.
sz connect-info                  # prints your pubkey@host:port

# Close a channel cleanly with the v1.3.0 --yes confirmation flag.
sz channels close --yes "<channel-id>"

Use sz init, NOT sz setup --auto. The --auto path connects to LQWD-AI-Grid (an LSPS2 JIT LSP node) which is a different onboarding flow. The LQWD channel faucet opens an inbound channel to your node directly, via the /register call shown below. Copy pubkey@host:port from sz connect-info into the registration payload.

name vs node-alias. The name field in the /register payload is a registration handle the LQWD gateway uses to identify your agent in its records. It is distinct from the LND (or LDK) alias — the string your node advertises on the Lightning gossip layer and prints from sz status or lncli getinfo. You can set both to the same string, but be aware that changing one does not change the other. The node alias is required for announced channels (see the "Configure a node alias" pre-flight above); the registration name is how LQWD looks you up after the fact.

Request a channel

Pass pubkey and node_uri to the same registration endpoint:

curl — channel faucet registration
curl -X POST https://api.lqwdclaw.bot/v1/internal/accounts/register \
  -H "Content-Type: application/json" \
  -d '{
    "name": "<pick-unique-node-name>",
    "pubkey": "03abc...",
    "node_uri": "03abc...@1.2.3.4:9735"
  }'

The response includes channel_granted: true, a channel_id, and next_steps.channel_status_url for polling. LQWD opens the channel asynchronously — expect 1 to 6 blocks for on-chain confirmation.

Check your channel status

From MCP: call lqwd_check_channel_status with your Bearer token. From REST:

curl — poll channel status
curl -H "Authorization: Bearer lqwd_YOUR_KEY" \
  https://api.lqwdclaw.bot/v1/internal/channel/status

States progress pending → pending_open (funding broadcast) → active (confirmed on-chain, routable).

Management surface

Plug in via MCP.

LQWD exposes a Model Context Protocol server at https://api.lqwdclaw.bot/v1/mcp. Streamable HTTP transport, version 2025-03-26. After registering, any MCP client with Bearer auth support can connect and see the account-management tools.

Tools

ToolPurposeCost
lqwd_registerRegister your mainnet node for the free Lightning channel. Requires pubkey + node_uri. Returns api_key for subsequent status polling and MCP tool calls.free
lqwd_check_balanceRead your account profile (tier, status, created_at).free
lqwd_check_channel_statusPoll your channel-faucet grant status.free

v1 ships account-management tools only. There is no paid service at this time; metered data tools are a later version.

Authentication. Authenticated tools require the HTTP header Authorization: Bearer <your_api_key> on every MCP request (where <your_api_key> is the lqwd_... key from lqwd_register). Same Bearer for all tools.

Claude Desktop

Add an entry to ~/Library/Application Support/Claude/claude_desktop_config.json (macOS) or equivalent path on other OSes:

claude_desktop_config.json
{
  "mcpServers": {
    "lqwdclaw": {
      "url": "https://api.lqwdclaw.bot/v1/mcp",
      "headers": {
        "Authorization": "Bearer lqwd_YOUR_KEY_HERE"
      }
    }
  }
}

Cursor / Cline / generic MCP client

Any MCP Streamable HTTP client. Point at https://api.lqwdclaw.bot/v1/mcp, set the Authorization header to Bearer <your_api_key>. The client will discover the account-management tools on first handshake.

Manual MCP call

If you're driving MCP from your own code rather than through a harness:

bash — initialize + register + check balance via MCP
# 1. Initialize the session, grab Mcp-Session-Id header
curl -D /tmp/h -X POST https://api.lqwdclaw.bot/v1/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"<pick-unique-node-name>","version":"1"}}}'

SID=$(grep -i mcp-session-id /tmp/h | awk '{print $2}' | tr -d '\r')

# 2. Register (unauthenticated — the tool that issues the key)
curl -X POST https://api.lqwdclaw.bot/v1/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"lqwd_register","arguments":{"name":"<pick-unique-node-name>"}}}'

# 3. Confirm your account profile with Bearer auth
curl -X POST https://api.lqwdclaw.bot/v1/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Mcp-Session-Id: $SID" \
  -H "Authorization: Bearer lqwd_YOUR_KEY" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"lqwd_check_balance","arguments":{}}}'

What's not in v1

  • Paid data tools / metered API access — no paid service exists at this time. Paid liquidity and metered tools are a later version. Existing endpoints that would be metered are not publicly advertised.
